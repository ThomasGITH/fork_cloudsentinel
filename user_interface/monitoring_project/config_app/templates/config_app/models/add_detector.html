Who does what?

Custom detectors are trusted server-side Python plugins. A developer implements the detector and a CloudSentinel operator validates, publishes and activates it. Python code cannot be uploaded directly through this browser.

1. Detector developer

Creates the plugin package, manifest and adapter.

2. CloudSentinel operator

Validates, publishes and explicitly activates an immutable release.

3. CloudSentinel user

Selects the detector during training and compares the resulting Saved Model artefacts.

Dependencies are not installed during publication. Every required dependency must already exist in the selected runtime profile. Changed plugin code must be published under a new version.

Training enabled

Uses cloudsentinel.training/v1 with metrics-partition-v1. The detector can train through the generic flow and its Saved Models can participate in comparisons.

Inference enabled

Requires cloudsentinel.inference/v1, metrics-matrix/v1 and a stable artifact format. Training alone does not make a model live-monitoring ready; the trained model also needs a valid live-input recipe.

Implement the adapter

validate_training checks dataset-dependent requirements. run_training trains, evaluates and returns a TrainingResult. The adapter may write only inside the artifact workspace supplied by its training context.

{{ training_adapter_example }}
Optional generic inference interface

load_model reconstructs a published artifact. predict_inference returns binary predictions and anomaly scores without exposing model internals.

{{ inference_adapter_example }}

Prediction semantics are 0 = normal, 1 = anomaly, and a larger anomaly score means more anomalous. Loaded models remain opaque to the generic host.

See {{ template_plugin_path }}/adapter.py for the complete skeleton and {{ lof_example_path }} for a working external scikit-learn example.

4

Validate, publish and activate

A CloudSentinel operator runs the existing wrapper from a trusted repository checkout. The plugin directory must be absolute, and --id and --version must match the manifest.

{{ publish_command }}

The wrapper uses a temporary administration environment, validates package structure, manifest and dependency compatibility, checks the adapter contract, publishes an immutable release, and activates it only because --activate is present. Temporary staging and administration resources are cleaned up.

  • requirements.lock never performs pip install.
  • External plugins cannot replace built-in detector IDs.
  • Publish changed code as a new version; releases are immutable.
  • Omit --activate when a release should be installed without changing the active version.
5

Confirm and use

  1. Refresh the Detector Library.
  2. Confirm that the detector shows source external.
  3. Open its details and inspect capabilities and input requirements.
  4. Select it in Train models.
  5. Train it beside one or more other detectors.
  6. Compare the resulting immutable Saved Model artefacts on the same evaluation dataset.
  7. Use goal-based comparison and robustness evidence across workload contexts to assess the result.

Detector not appearing?

  • The release may be published but not activated.
  • The ID may conflict with a built-in or another active detector.
  • The manifest may not satisfy schema version 1.
  • The entry point may not resolve to a valid adapter.
  • The adapter may not satisfy its declared contract.
  • A pinned dependency version may be absent from the runtime profile.
  • The Detector Library may need to be refreshed.
  • Inference remains unavailable when only training is implemented.

Check the manifest, validate again, publish changed code under a new version, activate the intended release, and refresh the Detector Library.
